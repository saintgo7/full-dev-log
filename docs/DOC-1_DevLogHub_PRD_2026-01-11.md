## 1. Executive Summary

### 1.1 Problem Statement

**현재 상황:**
개발팀의 작업 기록이 각자의 컴퓨터에 흩어져 있다. 마치 도서관의 책들이 각 사서의 집에 보관되어 있는 것과 같다. 누군가 "지난주에 인증 버그 어떻게 고쳤지?"라고 물으면, 모두가 자기 노트북을 뒤져야 한다.

**문제의 핵심:**
분산된 개발 로그로 인해 히스토리 추적 불가, 지식 공유 부재, 팀 학습 단절 발생

**영향:**
- 동일 문제 반복 해결로 인한 시간 낭비
- 신규 합류자 온보딩 지연
- 프로젝트 진행 현황 파악 어려움
- 암묵지 손실 (퇴사 시 지식 유출)

### 1.2 Proposed Solution

**해결 가설:**
각 개발자 PC에 로컬 에이전트를 설치하여 개발 활동을 자동 수집하고, 중앙 서버에 동기화하면 팀 전체의 개발 히스토리를 한 곳에서 검색/분석할 수 있다.

**핵심 가치:**
1. **자동 기록** - 개발자가 의식하지 않아도 모든 활동이 기록됨
2. **중앙 검색** - "그때 그 작업"을 30초 내에 찾을 수 있음
3. **팀 인사이트** - 프로젝트 진행 현황과 병목 지점 시각화

### 4.1 Core User Stories

| ID | As a... | I want to... | So that... | Priority |
|----|---------|--------------|------------|----------|
| FEAT-1 | 개발자 | 자동으로 개발 활동이 기록되길 | 별도 작업 없이 히스토리가 쌓임 | P0 |
| FEAT-2 | 개발자 | 과거 작업을 키워드로 검색하길 | 필요한 정보를 빠르게 찾음 | P0 |
| FEAT-3 | 팀 리드 | 팀 전체 활동을 대시보드로 보길 | 진행 현황을 파악함 | P0 |
| FEAT-4 | 개발자 | 프로젝트별로 로그를 그룹핑하길 | 관련 작업만 모아볼 수 있음 | P1 |
| FEAT-5 | 팀 리드 | 주간 리포트가 자동 생성되길 | 수동 정리 시간 절약 | P1 |
| FEAT-6 | 개발자 | 수동으로 메모를 추가하길 | 중요 맥락을 명시적으로 기록 | P1 |

### 4.2 User Story Details

#### FEAT-1: 로컬 에이전트 자동 수집

**Context:**
개발자가 코딩, 커밋, 빌드, 테스트 등 일상적인 개발 활동을 할 때 백그라운드에서 자동으로 기록

**Acceptance Criteria:**
```
Given: 에이전트가 설치되고 활성화된 상태
When:  개발자가 Git 커밋, 파일 저장, 터미널 명령 실행
Then:  해당 이벤트가 로컬 DB에 즉시 기록됨
```

**Out of Scope for FEAT-1:**
- 화면 녹화
- 키 입력 로깅 (보안 이슈)

#### FEAT-2: 중앙 검색 시스템

**Context:**
수집된 로그를 키워드, 날짜, 프로젝트, 작성자 등으로 검색

**Acceptance Criteria:**
```
Given: 중앙 서버에 로그가 동기화된 상태
When:  사용자가 "인증 버그" 키워드로 검색
Then:  관련된 모든 로그가 시간순으로 표시됨 (3초 이내)
```

#### FEAT-3: 웹 대시보드

**Context:**
팀 전체 활동 현황, 프로젝트별 진행도, 개인별 기여도 시각화

**Acceptance Criteria:**
```
Given: 로그인된 사용자
When:  대시보드 접속
Then:  타임라인, 통계 차트, 최근 활동이 표시됨
```

## 5. Scope Definition

### 5.1 MVP Capsule (10-Line Summary)

```
1. 목표: 분산된 개발 로그를 중앙에서 통합 관리
2. 페르소나: 개발자, 팀 리드, 신규 합류자
3. 핵심 기능: 자동 수집 에이전트 + 중앙 서버 + 웹 대시보드
4. 성공 지표: 개발 활동 90% 이상 자동 수집
5. 비기능 요구: 크로스 플랫폼(Win/Mac/Linux), 오프라인 지원
6. Out-of-scope: 실시간 협업, AI 분석, 모바일 앱
7. 리스크: 크로스 플랫폼 에이전트 개발 복잡도
8. 완화: Go 언어로 크로스 컴파일 용이성 확보
9. 실험: 1인 개발 + AI 협업으로 4주 MVP 달성 가능성 검증
10. 다음 단계: 오픈소스 커뮤니티 공개 및 확장
```

         낮음 ---------- 높음
              긴급도
```

|----------|----------|----------|

| P2 (Could) | 알림 시스템, 외부 연동 | No |

## 6. Assumptions & Risks

### 6.1 Key Assumptions

| ID | 가정 | 검증 방법 | 실패시 영향 |
|----|------|-----------|-------------|
| ASM-1 | 개발자는 자동 수집을 원한다 | 베타 피드백 | 수동 모드 옵션 추가 |
| ASM-2 | Go로 3개 OS 지원 가능 | PoC 개발 | 기술 스택 재검토 |
| ASM-3 | 4주 내 MVP 개발 가능 | 마일스톤 추적 | 범위 축소 |

### 6.2 Risk Board (Top 5)

| ID | 가정 | 리스크 | 완화 | 트리거 | 대응 |
|----|------|--------|------|--------|------|
| RISK-1 | 크로스 플랫폼 가능 | OS별 동작 차이 | Go 표준 라이브러리 활용 | PoC 실패 | Electron 전환 |
| RISK-2 | 4주 개발 가능 | 일정 지연 | AI 협업 극대화, MVP 축소 | 2주차 진척 30% 미만 | 핵심 기능만 출시 |
| RISK-3 | 로그 수집 부하 낮음 | 시스템 성능 저하 | 배치 처리, 샘플링 | CPU 5% 초과 | 수집 빈도 조절 |
| RISK-4 | 오프라인 동기화 안정 | 데이터 충돌/손실 | 충돌 해결 로직 | 동기화 실패 5% 초과 | 수동 해결 UI |
| RISK-5 | 오픈소스 관심 | 기여자 부족 | 좋은 문서화, 쉬운 기여 | 3개월 내 기여자 0명 | 마케팅 강화 |

**특별 고려 리스크:**
- 데이터 민감도: 중간 (코드 로그 포함 가능)
- 스케일 비용: PostgreSQL 무료, 서버 비용만 발생
- 벤더 락인: 없음 (오픈소스 스택)
- 법적 이슈: 없음

## 7. Experiment & Learning Loop

### 7.1 Initial Experiment

```

가설: 1인 + AI 협업으로 4주 내 MVP 개발 가능
